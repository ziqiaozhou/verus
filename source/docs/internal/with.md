# The `with` clause: extra ghost/tracked arguments

A `with` clause gives a function extra ghost or tracked inputs and outputs that
are **not** part of its executable signature. A caller supplies them with
`proof_with!`. Keeping the extras out of the real signature is what lets a trait
method with a *default body* carry them.

The extra inputs become extra parameters, and the extra outputs are folded into
the value the function returns, as `(ret, (extras...))`, so the rest of the
pipeline sees an ordinary function with one return value and needs no channel of
its own for the extras (see case 4).

The interesting part is the front end: rather than re-implementing type, borrow,
move, lifetime and variance checking of the extras, Verus arranges for **rustc**
to do it, by generating a *shim* whose parameter list contains the extras and
redirecting the call to it before type checking.

Three artifacts do the work:

| Artifact | Generated by | Purpose |
|---|---|---|
| `_VERUS_WITH_f` / `_VERUS_WITH_RET_f` | proc macro | call target carrying the extras as real parameters |
| the HIR redirect | `hir_proof_with_rewrite.rs` | rewrites a marked call to the shim, pre-typeck |
| `_VERUS_WITH_ARG_f` | proc macro | trait/impl conformance, in the correct variance position |
| `_VERUS_WITH_TR_Tr` | proc macro | blanket-implemented home for a trait method's shims |

After lowering, `fn_call_to_vir` maps the shim back to the original function, so
**VIR records a call to `f`** and `f`'s `requires`/`ensures` apply unchanged. The
spec is never copied onto the shim: one spec, one place. A shim is excluded from
VIR (its body is `unimplemented!()` and is never verified) and calling one
directly is rejected.

The examples below are simplified — attributes, spec plumbing and erasure
handling are elided.

## 1. Free function

```rust
// source
#[verus_spec(with Tracked(t): Tracked<&'a mut u8>)]
fn f<'a>(x: u8) -> u8 { proof!{ *t = x; } x }

#[verus_spec] fn caller() { proof_with!{Tracked(&mut a)} let r = f(1); }
```

```rust
// after the proc macro
fn f<'a>(x: u8) -> u8 {                     // extras are NOT in the real signature
    let __verus_with_in_0 = declare_with::<Tracked<&'a mut u8>>();
    let t = __verus_with_in_0.get();
    ...
}

#[verus::internal(with_shim)]               // sibling of `f`, under the same parent
fn _VERUS_WITH_f<'a>(x: u8, __verus_with_in_0: Tracked<&'a mut u8>) -> u8 {
    unimplemented!()
}

fn caller() { proof_with(...); let r = f(1); }   // the marker is still present
```

```rust
// after the HIR pass (before type checking)
fn caller() { let r = _VERUS_WITH_f(1, Tracked(&mut a)); }
//                    ^ rustc type-checks, borrow-checks and region-checks the extra
```

## 2. Inherent method

The same, nested in the `impl`:

```rust
impl S {
    fn m(&self, x: u8) { ... }

    #[verus::internal(with_shim)]
    fn _VERUS_WITH_m(&self, x: u8, __verus_with_in_0: Ghost<u32>) { unimplemented!() }
}

// s.m(1)  →  s._VERUS_WITH_m(1, Ghost(0))
```

## 3. Trait method

```rust
// source
#[verus_verify]
trait Tr {
    #[verus_spec(with Ghost(g): Ghost<u32> -> z: Ghost<u32>)]
    fn m(&self) { ... }                     // a default body is allowed
}

impl Tr for S {
    #[verus_spec(with Ghost(g): Ghost<u32> -> z: Ghost<u32>)]
    fn m(&self) { ... }
}
```

```rust
// after the proc macro: the companion stays on the trait, the shims move to a
// generated sibling trait that every implementor gets for free
trait Tr {
    fn m(&self) { ... }

    // the conformance companion: the trait's OUTPUTS go in, its INPUTS come out.
    // An associated function with no receiver, and never called.
    #[verifier::external_body]
    fn _VERUS_WITH_ARG_m(__verus_with_chk_out_0: Ghost<u32>) -> (Ghost<u32>,)
        where Self: Sized
    { unimplemented!() }
}

#[verus::internal(with_shim_trait)]
trait _VERUS_WITH_TR_Tr: Tr {
    #[verus::internal(with_shim)]
    fn _VERUS_WITH_m(&self, __verus_with_in_0: Ghost<u32>) { unimplemented!() }

    #[verus::internal(with_shim)]
    fn _VERUS_WITH_RET_m(&self, __verus_with_in_0: Ghost<u32>) -> ((), (Ghost<u32>,)) {
        unimplemented!()
    }
}
impl<T: Tr + ?Sized> _VERUS_WITH_TR_Tr for T {}

impl Tr for S {
    fn m(&self) {
        // the extras are ordinary bindings in the body, exactly as in case 1
        let __verus_with_in_0 = declare_with::<Ghost<u32>>();
        let g = __verus_with_in_0.view();
        let mut z = declare_ret_with::<Ghost<u32>>();
        ...                             // the body assigns `z`, e.g. proof!{ z = Ghost(..) }

        // conformance: a closure that is never called, with parameters of its
        // own. Only its signature matters — see below.
        let _verus_with_conform_check = |__verus_with_chk_out_0: Ghost<u32>| {
            let (__verus_with_chk_in_0,): (Ghost<u32>,) =
                Self::_VERUS_WITH_ARG_m(__verus_with_chk_out_0);
        };
    }
    // no shim methods here: the blanket impl supplies them
}
```

The extras never travel through the companion. `g` comes from `declare_with()`
and `z` is a local the body assigns, just as for a free function; the companion
call exists only so that rustc has to relate the impl's extra types to the
trait's. It is written as an uncalled closure with fresh parameters so that no
value of the user's is involved and nothing is evaluated at run time.

The shim trait mirrors the trait's generics, where-clauses and per-method
`where Self: Sized` bounds, and takes the trait as a supertrait, so the blanket
impl reaches every implementor — including `dyn Tr` and a type parameter bounded
by `Tr` — while leaving the user's trait surface to the companion alone. The
companion cannot move with the shims: it is what each impl overrides, which is
how the impl's extras are checked against the trait's.

Because the shims live on a trait the user never named, they are *not* in scope
at the call site (E0599), and rustc's `trait_map` does not help: it lists only
traits in scope carrying an item of the called *name*, so the shim trait never
appears there naturally. The HIR pass therefore injects a
`rustc_hir::TraitCandidate` for the shim trait at each rewritten call site,
reusing the `import_ids` of the candidate already recorded for the original
method so no "unused import" lint fires.

The injection is deliberately narrow: it is keyed on the `HirId` of the call
being rewritten, and only traits that were already candidates *there*, whose
shim trait declares the shim being called, contribute. Putting a shim trait in
scope for a whole body would let a hand-written `s._VERUS_WITH_m(..)` resolve
somewhere the user never brought it in.

`find_original_fn_for_shim` recovers `m` from the shim by stripping the prefix
and asking the shim's parent — the trait, the impl, or the module — for the
sibling of that name; when the parent is marked `with_shim_trait` it instead
looks for `m` in the supertraits, and accepts only if exactly one of them has an
associated function of that name.

Since the call site is checked against the shim trait, it is checked against the
**trait's** extras rather than any particular impl's. That is the intended
reading — a generic caller has nothing else to go on — and the companion is what
holds each impl to it.

### Why the companion is shaped that way

`Ghost<A>` and `Tracked<A>` are `PhantomData<A>`, hence covariant. At a virtual
call the caller supplies an extra input at the *trait's* type and receives an
extra output at the trait's type, so soundness needs ordinary function
subtyping:

- extra **inputs** contravariant — `I_trait <: I_impl`, the impl must accept
  anything a caller may send;
- extra **outputs** covariant — `O_impl <: O_trait`, the impl may promise more,
  never less.

Passing the impl's extras *into* a shim typed at the trait's types checks both
of these backwards, and covariance lets rustc shrink both sides to their
intersection and accept. Having the value flow *out of* the companion is what
puts each side in the position with the correct variance. When the method has
lifetime parameters the companion carries a vacuous `where 'x: 'x` for each,
which makes them early-bound so they can be turbofished; without that,
late-bound lifetimes cannot be named at the call.

This check is enforced by rustc, so it also works when the impl is in a
**downstream crate** — a case Verus cannot check itself, since an upstream crate
cannot enumerate its downstream impls.

## 4. Extra outputs at the call site

```rust
proof_with!{Ghost(1u32) => Ghost(z): Ghost<u32>}  let r = f(x);

// →
let (r, (z,)) = _VERUS_WITH_RET_f(x, Ghost(1u32));
```

`=> _` discards the extras. It still reaches the callee at the folded return
type, so the call is built at that type and field 0 is read back out; which form
the call site used is decided by whether the *callee* has registered extras,
never by the shape of the destination, since a callee that genuinely returns a
2-tuple has the same shape as a destination carrying extras.

### How the fold is produced

The macro leaves the Rust signature completely alone — a `with` clause adds no
parameter and changes no return type, which case 3's default bodies and every
unverified caller depend on. Only the `ensures` clause is written against the
folded pair, which is legal without touching the signature because
`ensures<A>(_a: A)` is generic in its argument.

Lowering then splits the body in two:

1. the declarations of the extra outputs, `let mut z = declare_ret_with()`, are
   hoisted out. They must sit *above* the header calls, since a header is only
   allowed at the very beginning of a body, and hoisting is safe because the
   declaration has no initialiser;
2. what remains is translated as an ordinary expression, and its value is paired
   with the outputs — at the tail, and at every `return`.

Reading a ghost-mode output into the returned tuple goes through the same node
`Ghost(..)`/`Tracked(..)` produce in exec code, so the read is checked inside a
ghost block and the tuple stays exec. Two shapes need care: a body that always
leaves through a `return` has no value to pair and stays diverging, and a body
whose value is a `proof` block is sequenced as a statement with a fresh unit
paired in its place, so the tuple does not become ghost.

## 5. External free function (`assume_specification`)

The proxy carries the clause, but the shim is named after the **target**, since
that is what a call site resolves to.

```rust
// source
#[verifier::external]
fn ext(x: u64) -> u64 { x }

#[verifier::external_fn_specification]
#[verus_spec(ret =>
    with Tracked(t): Tracked<&u64>
    ensures ret == x,
)]
fn ext_spec(x: u64) -> u64 {
    ext(x)                                  // the body names the target
}

#[verus_spec] fn caller(a: u64) { proof_with!{Tracked(&a)} let r = ext(1); }
```

```rust
// after the proc macro
fn ext_spec(x: u64) -> u64 {                // the proxy's signature is untouched
    let __verus_with_in_0 = declare_with::<Tracked<&u64>>();
    let t = __verus_with_in_0.get();
    ext(x)
}

// named `_VERUS_WITH_ext`, not `_VERUS_WITH_ext_spec`, and a sibling of the proxy
#[verus::internal(with_shim)]
fn _VERUS_WITH_ext(x: u64, __verus_with_in_0: Tracked<&u64>) -> u64 { unimplemented!() }

fn caller(a: u64) { proof_with(...); let r = ext(1); }
```

```rust
// after the HIR pass
fn caller(a: u64) { let r = _VERUS_WITH_ext(1, Tracked(&a)); }
```

The target name is read out of the proxy's body by `external_fn_target_name`,
and the extras are registered against the `DefId` that `get_external_def_id`
resolves — the external function, never the proxy — because that is the callee
every call site names.

## 6. External trait (`external_trait_specification`)

The same redirection, one level up: the clause is written on the proxy trait,
and everything it generates is keyed to the **foreign** trait.

```rust
// source
#[verifier::external]
trait T { fn f(&self, a: u64) -> u64; }

#[verus_verify]
#[verifier::external_trait_specification]
trait ExT {
    type ExternalTraitSpecificationFor: T;

    #[verus_spec(r =>
        with Ghost(g): Ghost<u64>
        requires g == 1,
        ensures r == a,
    )]
    fn f(&self, a: u64) -> u64;
}

#[verus_spec]
fn caller<S: T>(s: &S) { proof_with!{Ghost(1u64)} let r = s.f(2); }
```

```rust
// after the proc macro
trait ExT {
    type ExternalTraitSpecificationFor: T;
    fn f(&self, a: u64) -> u64;
    // no conformance companion: see below
}

// the supertrait is the FOREIGN trait, so the blanket impl reaches every
// implementor of `T` — including ones in other crates, and `dyn T`
#[verus::internal(with_shim_trait)]
trait _VERUS_WITH_TR_ExT: T {
    #[verus::internal(with_shim)]
    fn _VERUS_WITH_f(&self, a: u64, __verus_with_in_0: Ghost<u64>) -> u64 {
        unimplemented!()
    }
}
impl<X: T + ?Sized> _VERUS_WITH_TR_ExT for X {}
```

```rust
// after the HIR pass
fn caller<S: T>(s: &S) { let r = s._VERUS_WITH_f(2, Ghost(1u64)); }
```

The blanket impl is legal even though `T` is foreign, because the shim trait is
*local* — the orphan rules permit `impl<X: ForeignTr + ?Sized> LocalTr for X {}`
the same way they permit `impl<T: Iterator> Itertools for T`. Nothing has to be
added to the trusted items generated for an external trait.

Two lookups have to be redirected, because the proxy's name and module are not
derivable from the foreign trait:

- **finding the shim trait.** `_VERUS_WITH_TR_ExT` is named after the proxy and
  lives in the proxy's module, so the usual "sibling of the trait, by name"
  search cannot find it from `T`. The shim trait is instead recognised by the
  supertrait bound its blanket impl needs anyway: among the traits marked
  `with_shim_trait`, the one whose supertrait is `T`. Supertrait bounds and
  attributes both cross a crate boundary, so the same rule can serve a foreign
  proxy later.
- **registering the extras.** Call sites and impls resolve to `T::f`, so the
  extras the proxy declares are registered against `T::f`, exactly as case 5
  registers against the external function rather than the proxy.

### What is still missing: conformance

`_VERUS_WITH_ARG_f` works by being *overridden* in each impl, which is what puts
the impl's types and the trait's in opposite variance positions (see case 3). An
`impl T for S` can only contain items of `T`, so a proxy has nowhere to put the
override, and no companion is emitted. Nothing currently checks an impl's extras
against the proxy's; today this is sound only because an impl of a foreign trait
has no way to *declare* extras of its own, so it can only inherit the proxy's.

A `with` clause on an impl of a foreign trait that has no
`external_trait_specification` declaring those extras cannot work at all, and
that limit is inherent: there is no trusted declaration to check the impl
against.

Because the shims have default bodies *and* are blanket-implemented, an impl that
does not override a defaulted method still gets them:

```rust
#[verifier::external] trait T { fn g(&self) -> u64 { 2 } }
impl T for S {}                             // never overrides `g`

proof_with!{Ghost(1u64)} let q = s.g();     // still finds the shim
```

A design that gave the shims no default body could not serve this case, as the
empty impl would then supply nothing to call.

A `with` clause on a proxy method that has a *default body of its own* is still
rejected: that form reaches a different arm of the macro, where the target the
shims must be named after has not been resolved.

## Rules worth knowing

**A `with` parameter must name its lifetimes explicitly.** The written type is
replayed in two positions where elision means opposite things: in the shim
signature, an elided lifetime is a fresh universally-quantified parameter chosen
by the caller; in the body's `let ... = declare_with()`, it is an inference
variable solved from the body — which can silently reach `'static`, letting the
callee assume a borrow the caller never granted. The check reads the type **as
written**, never `node_type()`, whose regions are erased.

**Extras are registered before any body is lowered.** Registering them while
lowering each callee made the result depend on definition order: a caller
lowered before its callee saw no extras.

**The reserved name is a convention, not a mechanism.** A shim is recognised by
its `#[verus::internal(with_shim)]` attribute, so a user function that merely
collides with the name stays an ordinary function.

**Shims are emitted in stub-erase mode as well as full mode.** A shim is a
signature-level artifact and belongs with the ghost stubs, not the ghost bodies;
otherwise a downstream crate cannot resolve it. Only `erase_all` omits them.

**A foreign callee's extras are recovered from its shim's signature** rather
than from imported VIR, so that rustc's view and Verus's view derive from one
artifact and cannot drift.

## Follow-ups

**External trait conformance** (case 6). An impl's extras are not checked
against the proxy's, because there is no per-impl companion to override. Either
find another home for the override, or check the declared extras directly,
accepting that the variance argument then rests on Verus rather than on rustc.

**A foreign proxy's shim trait is not found across a crate boundary.** The
supertrait search runs over the local crate's traits only. The rule itself
carries over — supertrait predicates and attributes both cross crates — but the
search has to be extended to the crates in scope.

**Extras discovery still reads the body.** `pre_scan_declare_with_params` finds
extras by scanning for `declare_with()` calls, which is why a bodyless trait
method needs the shape heuristic in `headers.rs::make_trait_decl`, and why
extras must be pre-registered before any body is lowered. Reading them from the
shim's signature instead would make discovery uniform for bodied and bodyless,
local and foreign, and would remove both workarounds.

**Multiple call-site outputs need one ascribed tuple**, because
`WithSpecOnExpr.outputs` is a single pattern.
